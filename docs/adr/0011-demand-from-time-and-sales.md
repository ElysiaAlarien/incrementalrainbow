# Demand is a function of time and of recent sales

The demand of a color in a market is drift times saturation, and its price is the base price times demand. `DemandState` (in `src/core/state/`) holds the rules.

**Drift is a pure function of time.** At the start of a game, the core draws one u32, the drift key, from its random number generator. The key, a hash of the market and color ids, and a knot index seed a `SimRng` that gives the value of that knot. Drift moves smoothly (smoothstep) from one knot to the next, once each `drift_period_ms`. We rejected a random walk that draws from the generator on each tick, for three reasons:

- One long tick must give the same state as many short ticks (ADR-0008). A draw on each tick breaks this, unless time is cut into fixed steps.
- Each tick must take time in proportion to the size of the state, not the duration. Fixed drift steps make offline progress for a day cost one step for each period of that day.
- The demand at a future time is known. The forecast can show this true demand with noise that research removes. Demand events and other rules that draw from the generator do not change drift.

A knot value depends only on the key, the ids, and the index. So a change to the drift rule, the hash, or the ids of markets and colors changes the demand of every saved game. The version 3 save fixture pins drift values, so such a change fails a test, and it needs a save migration.

**Saturation is the time when it has fully recovered.** For each color in each market that has saturation, the state holds `saturated_until_ms`. A sale of n widgets at time t sets it to `max(saturated_until_ms, t) + n * saturation_ms_per_widget`. Saturation recovers at a constant rate, so the recent widgets that it still holds at time t are `(saturated_until_ms - t) / saturation_ms_per_widget`, and its factor is `1 / (1 + widgets / saturation_half_widgets)`. All of the state is integer time, so it is exact, and a tick changes it only to forget saturation that has fully recovered. We rejected exponential recovery, because a decay on each tick is not exact in floats across tick lengths, and because `pow` and `exp` can give different bits on different platforms.

**A sale uses the demand at the arrival of its shipment**, which can be before the end of a long tick. All widgets of one shipment sell at one price, and then the sale saturates.

**Demand events are draws at their start times.** A demand event multiplies the demand of its colors in every market, from its start up to its end: by `1 + size` for a spike, and by `1 - size` for a crash. Overlapping events multiply. The state holds the time of the next start. The tick treats that time as an event in its loop (ADR-0008). When the loop reaches it, the random number generator chooses the event, and then the time of the next start. So the draws happen at fixed simulated times in a fixed order, and ticks of any length give the same events. At one time, shipments arrive first and sell at the demand from before the event, then events start, then automatic shipments. We rejected events as a pure function of time, like drift, because the issue asks for the seeded generator, and because each active event is then state that a save keeps: a change to the list of events in the data does not change events that have started. A save from before demand events has no next start. The first tick after the load sets it, so that the migration does not draw from the generator.

**The forecast is the demand at a future time with noise in its drift (#17).** The forecast of a color in a market at time T is drift times saturation times event factors, as at a sale, with two changes. The drift is `lerp(noise, real drift, accuracy)`. The noise is a second drift curve with the same period and amplitude. Its knots come from the drift key and from a hash of `"forecast\n" + market` and the color. Saturation and events are those of the state now, as they will be at T. So with an accuracy of 1, no more sales, and no new event, the forecast is the real demand at T. The accuracy is `forecast.base_accuracy` in `balance.json` plus the `forecast_accuracy` of each complete research, at most 1.

- The noise is a pure function of the drift key, the ids, and T, like drift. A forecast draws nothing from the random number generator, so a query cannot change the future demand, and the same seed gives the same forecast. The noise moves smoothly with T, so the forecast on the screen does not jump from frame to frame. We rejected a new key drawn from the generator: that draw changes the demand events of every seed, and a migration cannot draw one for an old save.
- The forecast needs no saved state. The drift key and the complete research are in the save, so a load gives the same forecast and accuracy, and there is no save migration for it. The accuracy comes from the `forecast_accuracy` values in the current data, as color unlocks do. So a change to those values changes the accuracy of an old save too.
- A demand event that has not started is not in the forecast. The generator chooses it at its start, and story 45 asks for events as surprises. A copy of the generator could show future events, but then research would remove the surprise. Saturation and the events that have started are state that the player already sees, so the forecast has them, with no noise.
- At an accuracy of 0, the forecast drift and the real drift are independent values in the same range. The base accuracy is low, so at the start the forecast is nearly random.

**Generated markets reuse the drift key (#12).** Generated market n is a pure function of the drift key, n, and the generator rules in `markets.json`, like a drift knot. The save keeps only the count of generated markets and the state of each market (population, income, investments, and capacity used). The load makes the markets again from the key. We rejected a new draw from the random number generator for a key of its own, because it moves every later draw, such as the demand events of the pinned save fixtures, and old saves have no such key. We rejected saving each generated market in full, because it duplicates what the rules give. The cost: a change to the generator rules changes the names, remoteness, and base prices of the generated markets in saved games, as a change to the hand-made markets does.

**Fast queries keep the same results (#55).** With 39 colors and many markets, `Simulation.markets()` and `Simulation.forecast()` were too slow for each frame. They now get all colors of a market in one call (`DemandState.demands` and `DemandState.forecasts`). The parts that are the same in each market are computed once for the query (`DemandState.Moment`). Knot values and pair hashes are in caches. Each query also computes a few knot values of the knot after the next one, so that no query computes the knot values of all markets when the time reaches a new knot. The caches are not state: a knot value depends only on its seed, so a new `DemandState` computes the same values, and a query still draws nothing from the random number generator. Each value comes from the same float operations in the same order as before, so the results are the same to the bit. `BigNumber` has fast paths for the most common mantissa sizes that give the same bits as the slow path. A test compares the results of a fixed game with hashes from the queries before #55 (`tests/fixtures/query_results.json`). A change of a query that changes a result fails it, and if the change is meant, `tools/make_query_results.gd` writes the hashes again.
